# Сценарии локальной demo-версии

## Назначение режима

Demo-режим предназначен для эксперта, у которого нет отдельных MAX-аккаунтов для каждой роли. Он запускает тот же React frontend, Nest API и SQLite, но принимает локальный заголовок пользователя и показывает переключатель ролей. Переключатель собирается только при `VITE_DEMO_MODE=true`.

Demo-режим нельзя публиковать как production: `MAX_WEBAPP_AUTH=off` допустим только вместе с `NODE_ENV=development`.

## Запуск одной командой

Требования: Docker Desktop с Compose v2 и доступ к Docker Hub при первой загрузке образов.

```bash
npm run demo:docker
```

Открыть:

- приложение: http://localhost:8080;
- проверка API: http://localhost:8080/api/health.

Ожидаемый health-ответ:

```json
{"ok":true,"service":"barber-academy-api"}
```

При первом запуске Compose собирает frontend и backend, создаёт volume `barber_data`, запускает API и идемпотентный seed. Повторный запуск не должен удалять созданные экспертом сообщения, работы и загрузки.

Если загрузка `node:20-bookworm-slim` завершается `TLS handshake timeout`, это недоступность Docker Hub из Docker Desktop, а не ошибка Dockerfile. Исправьте proxy/VPN Docker Desktop и повторите команду.

## Переключение ролей

В верхней части приложения расположен переключатель «Локальная демо-роль»:

| Роль | Локальный MAX ID | Что проверяется |
| --- | ---: | --- |
| Ученик | `1000000001` | работы, файлы, профиль, уведомления, чат |
| Преподаватель | `1000000002` | ученики, проверка работ, оценки, чат |
| Администратор | `1000000003` | пользователи, назначения, заявки, аудит |

Гостевой раздел «Портфолио» доступен без авторизации. Дополнительные ученики нужны для проверки поиска и полного списка преподавателя: Анна Модель (`1000000011`) и Илья Барбер (`1000000012`).

## Сквозной сценарий эксперта

### 1. Гость

1. Откройте «Портфолио».
2. Найдите ученика по части имени.
3. Откройте карточку ученика.
4. Проверьте описание, метро, преподавателей, рейтинг и одобренные работы.
5. Убедитесь, что на странице нет телефона, MAX ID, username, неопубликованных работ и приватных сообщений.
6. Закройте карточку кнопкой, клавишей `Escape` и нажатием на фон.

Ожидается: видны только активные ученики и только одобренные работы; изображения не ломают разметку даже при ошибке загрузки.

### 2. Ученик

1. Выберите роль «Ученик».
2. На главной проверьте сводку и быстрые действия.
3. В «Работах» откройте pending- и approved-карточки.
4. Проверьте статус, оценку 1–5, отзыв и комментарии.
5. Добавьте комментарий к своей работе.
6. В профиле создайте новую работу с PNG/JPEG/WebP, MP4 или PDF.
7. Проверьте предпросмотр изображения, блокировку кнопки во время запроса и сообщение об успехе.
8. Откройте новую работу; убедитесь, что файл доступен владельцу, но ещё отсутствует в гостевом портфолио.
9. Загрузите аватар.
10. Измените публичное описание.
11. Подайте заявку на изменение имени, телефона и метро.
12. Отправьте приватную обратную связь.
13. Откройте уведомления и отметьте их прочитанными.
14. В чате отправьте сообщение назначенному преподавателю.

Ожидается: ученик не видит чужие работы или диалоги; повторное нажатие не создаёт дубликаты; технические JSON-значения не показываются пользователю.

### 3. Преподаватель

1. Выберите роль «Преподаватель».
2. Откройте сводку: должны быть количество ожидающих работ и все назначенные ученики, в том числе без pending-работ.
3. Найдите ученика по имени.
4. Откройте его работы и выберите новую работу из предыдущего раздела.
5. Добавьте комментарий.
6. Отправьте работу на доработку с объяснением.
7. Переключитесь на ученика, откройте уведомление и отправьте исправление с файлом.
8. Вернитесь к преподавателю, поставьте оценку от 1 до 5 и одобрите работу.
9. Проверьте, что работа появилась в публичном портфолио.
10. Ответьте ученику в чате.

Ожидается: преподаватель работает только с назначенными учениками; телефон, MAX ID и username ученика не выдаются преподавательским API.

### 4. Администратор

1. Выберите роль «Администратор».
2. Проверьте сводку и список учеников.
3. Используйте поиск и откройте карточку ученика.
4. Создайте тестового ученика и отредактируйте его данные.
5. Создайте преподавателя или выдайте существующему пользователю роль преподавателя.
6. Назначьте преподавателя ученику, затем снимите назначение.
7. При наличии импортированной или демо-заявки преподавателя рассмотрите её как legacy-сценарий; новые доступы создаются по номеру в разделе «Управление».
8. Одобрите или отклоните заявку ученика на изменение профиля.
9. Откройте приватную обратную связь.
10. Убедитесь, что административные операции появились в журнале аудита.

Ожидается: опасные действия требуют подтверждения; после операции интерфейс обновляется; ученик и преподаватель получают `403` на административных маршрутах.

### 5. Пользователь без роли

Этот сценарий проверяется API smoke-тестом и в реальном MAX. Новый пользователь должен увидеть onboarding с запросом подтверждённого контакта, а не закрытые вкладки. Неизвестный номер остаётся гостем. Заранее назначенный администратором номер после проверки подписи получает соответствующую роль; ручной ввод MAX ID отсутствует.

## Файлы

Проверьте хотя бы один файл каждого поддерживаемого вида:

- JPEG, PNG и WebP;
- MP4 и MOV;
- PDF.

Проверьте также ошибочные случаи: файл больше лимита, неподдерживаемая сигнатура, повторная отправка и попытка открыть файл другого ученика. Публичная ссылка должна работать только после одобрения работы.

Seed-изображения `demo-*.png` являются безопасными статическими ассетами frontend. Файлы, которые эксперт загрузит через форму, сохраняются как записи `stored_files` и данные в Docker volume.

## Автоматическая smoke-проверка

Smoke-тест использует отдельные временные SQLite и uploads, дважды запускает seed, поднимает локальный API и проверяет роли, активацию по подтверждённому номеру, гостевой режим неизвестного номера, приватность, чат и реальный PNG-файл:

```bash
npm run build -w backend
node testing/api-smoke.mjs
```

Ожидаемый результат: `API smoke: PASS`. Временные данные удаляются даже после ошибки.

Основной набор проверок:

```bash
npm test
npm run lint
npm run build
docker compose -f docker-compose.yml -f docker-compose.local.yml config --quiet
```

## Сохранение, остановка и повторный запуск

Остановить приложение, сохранив базу и файлы:

```bash
docker compose -f docker-compose.yml -f docker-compose.local.yml down
```

Повторно запустить те же данные:

```bash
docker compose -f docker-compose.yml -f docker-compose.local.yml up
```

Проверьте, что созданная работа и сообщения остались на месте. Обычный `down` не удаляет named volume.

Полный сброс только локального demo-volume:

```bash
docker compose -f docker-compose.yml -f docker-compose.local.yml down -v
npm run demo:docker
```

`down -v` необратимо удаляет demo-БД и demo-загрузки. Эту команду нельзя выполнять с production Compose/volume.

## Известные границы demo

- MAX init data в этом режиме не проверяется; строгая проверка описана в `PRODUCTION_USER_SCENARIOS.md`.
- Локальная версия не подтверждает работу домена, TLS, карточки бота или мобильного клиента MAX.
- Первая Docker-сборка требует доступа к Docker Hub. Уже загруженные образы и собранные слои позволяют повторный запуск без сети.
